# PharmacyERP — خطة التطوير والعرض

الخطة الكاملة مبنية على الكود الموجود، مقارنة السوق، و[محاكاة شهر تشغيل](30-day-operations.md). الهدف الأول عرض مسار شغل كامل من استلام الدفعة لحد البيع وتقفيل الشيفت، ثم تجربة فرع واحد بعد اجتياز اختبارات التشغيل. افتراض التخطيط سلسلة في مصر عندها فروع ومخزن مركزي. نطاق الربط والضرائب والعمل وقت انقطاع الشبكة يتأكد مع العميل.

## المعمارية والبيانات

React SPA متصلة بـAPI من نفس الـorigin في التشغيل المقترح. الـAPI تطبيق واحد مقسم حسب الهوية والفروع، الكتالوج، المخزون، المبيعات، المشتريات، التحويلات والتقارير. SQL Server هو مصدر الحقيقة. المخزون يبدأ بسجل حركات غير قابل للتعديل من الواجهة، ورصيد دفعة/موقع بيتحدث في نفس المعاملة مع الحركة. التصحيح بحركة عكسية موثقة.

- **Catalog:** صنف، وحدات وتحويلاتها لوحدة أساس، باركود لكل وحدة، وسعر له تاريخ سريان. دعم GS1 DataMatrix يتحدد حسب ملصقات العميل والماسح. [GS1 General Specifications](https://ref.gs1.org/standards/genspecs/)
- **Stock:** Lot مرتبط بالصنف والصلاحية، ورصيد حسب الموقع والحالة. حجز وخصم وتوزيع FEFO ذري بتزامن على قاعدة البيانات. في التحويل، الشحن ينقل الرصيد لقيد النقل والاستلام يضيف للموقع المستلم حسب الحالة والكمية الفعلية.
- **Sales:** Sale وSaleLine وتخصيص دفعات ومدفوعات وشيفت ومرتجعات مرتبطة بالأصل. مبالغ Decimal، قواعد تقريب ووحدات متفق عليها، وSnapshot للسعر والضريبة وقت البيع.
- **Operations:** أمر شراء واستلام ومرتجع مورد، جرد وتسوية، طلب تحويل وشحنة واستلام، حدث Audit للإجراءات الحساسة.
- **API:** عقود OpenAPI مع DTOs واضحة، Pagination وفلاتر، وحالات خطأ موحدة. أمثلة للمسارات `/sales`، `/sales/{id}/returns`، `/transfers/{id}/ship`، `/transfers/{id}/receive`، `/purchase-orders/{id}/receipts`، `/shifts/{id}/close`. عمليات البيع والاستلام والمرتجع تستخدم معرف إعادة محاولة فريد. لو الرد ضاع بعد الحفظ، الواجهة تستعلم عن نفس العملية قبل محاولة دفع جديدة.

## الشاشات وتجربة الاستخدام

| الشاشة | ترتيب المحتوى والعمل |
|---|---|
| دخول واختيار موقع | تسجيل الدخول، المواقع المصرح بيها، اسم الفرع والشيفت في الشريط العلوي |
| POS | بحث أو مسح بفوكس ثابت، نتيجة واضحة بالوحدة والسعر والمتاح، سلة وإجمالي ثابتين، دفع، إيصال وإعادة طباعة. المرتجع يبدأ بالبحث عن الإيصال |
| الخزنة والشيفت | العهدة ووسائل الدفع، حركات نقدية، إدخال النقد الفعلي، فرق وسبب واعتماد |
| الكتالوج | بحث عربي وإنجليزي وباركود، وحدات وأسعار، معاينة الاستيراد وتقرير الاستثناءات |
| المخزون والجرد | فلاتر الموقع والحالة، تفاصيل الدفعات، سجل حركة، جرد وعزل وتتبع سحب |
| التحويلات | قوائم حسب المرحلة، طلب واختيار صنف وكمية، شاشة تجهيز، شاشة استلام وفروق |
| المشتريات والموردون | أوامر مفتوحة ومتبقي، استلام دفعات ومطابقة كميات وأسعار، مرتجع مورد |
| Dashboard والتقارير | تنبيهات فيها إجراء مباشر، نواقص وصلاحية وتحويلات متأخرة وفروق خزنة. فلترة من الفرع للدفعة أو الفاتورة |
| الإدارة | مستخدمون وأدوار ومواقع وجلسات وسجل تدقيق، مع عرض حالة التشغيل للمصرح لهم |

اتجاه بصري هادي بأسطح فاتحة ولون إجراء واحد، وحالات المخزون والأخطاء بتظهر بنص وأيقونة. واجهة عربي RTL وإنجليزي LTR، وفوكس ظاهر، واختصارات متاحة من الـPOS، ورسالة خطأ تفضل جنب الإجراء. الكاشير يقدر يتمم البيع بالكيبورد والماسح، والمخزن يقدر يسجل استلام من تابلت بعد اختبار الحجم الفعلي. نعتمد أولًا مكونات الأزرار والحقول والجداول والتنبيهات وحالات التحميل والفشل من [Tech Stack](tools.md).

## مراحل التنفيذ

| المرحلة | الشغل | شرط الخروج |
|---|---|---|
| 0 — تثبيت النطاق | مشاهدة شيفت واستلام وتقفيل، عينة Catalog/رصيد مصرح بيها، أجهزة وشبكة، ومراجعة التكاملات | سيناريو عرض وأولويات متفق عليها ومتطلبات Pilot محددة |
| 1 — أساس التشغيل | قاعدة جديدة بمهاجرات وبيانات اختبار، إصلاح FEFO والتزامن، صلاحيات المواقع، OpenAPI، وهيكل React وRTL | إنشاء قاعدة من الصفر، نجاح بيع آخر وحدة بالتزامن وبيع من دفعتين، والتحقق من عزل المواقع |
| 2 — أول عرض | تشغيل المسار على API حقيقي ببيانات تجريبية. استلام دفعة، بيع، طباعة، تحويل جزئي، وتنبيه أو فرق شيفت قابل للتتبع | تجربة السيناريو من أول لآخر على جهاز العرض وماسح وطابعة متوافقين، وقياس زمن إدخال الفاتورة مع المستخدم |
| 3 — تجهيز Pilot | تكملة المرتجعات والمشتريات والجرد والمطابقة، استيراد تجريبي، استعادة، قياس حمل حسب عدد الأجهزة، اعتماد الإجراءات والربط المطلوب | مطابقة الأرصدة والإيصالات، نجاح اختبارات الفشل والرجوع، تدريب ودعم متفق عليه |
| 4 — Pilot فرع واحد | تجربة مراقبة بمسار رجوع للنظام الحالي ومطابقة يومية، ثم قرار توسيع | نتائج مطابقة وتقييم فريق الفرع وموافقة العميل قبل ضم فروع إضافية |

نبدأ بمسار رأسي واحد يشمل شاشة البيع وقواعدها وقاعدة بياناتها واختبارها. بقية الشاشات تتنقل تدريجيًا، ونحتفظ بالنسختين الحاليّتين كمرجع للوظائف. التأمين والولاء والتوصيل والمتجر والمحاسبة العامة تتحدد حسب الأولوية والتكامل مع نظام العميل.

## قرارات تحتاج بيانات العميل قبل التشغيل

- هل الاتصال بيقع وقت الزحمة، وهل لازم البيع يكمل وقت الانقطاع؟ إعادة المحاولة بعد timeout تعالج الرد المفقود. البيع أثناء انقطاع كامل يتطلب سياسة واضحة للمخزون والمدفوعات ومزامنة الأجهزة أو تشغيل محلي للفرع، ويتاختبر قبل الإطلاق لو مطلوب.
- إيه صيغة التصدير وحجم الكتالوج والدفعات وكمية الفواتير وقت الذروة؟ تجربة الاستيراد تشمل كشف أخطاء ومطابقة أرصدة مع العميل. أهداف السرعة والحمل تتحدد على عينة العميل وجهازه.
- إيه المطلوب من الإيصال الإلكتروني والضرائب وبيانات العملاء والربط المحاسبي؟ نؤكد الانطباق مع العميل ومحاسبه، ونختبر الربط في بيئة الاختبار قبل التشغيل إذا كان مطلوبًا. [مصلحة الضرائب المصرية](https://eta.gov.eg/ar/content/e-receipt-services)

المسار الأول للتنفيذ هو تهيئة SQL Server وإصلاح البيع على دفعتين بالتزامن مع تصميم تدفق الـPOS، ثم ربط شاشة React بعقد البيع واختبار العملية من البحث لحد إعادة الطباعة.
